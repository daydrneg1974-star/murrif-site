# Серверная форма murrif.ru: установка после согласования

Эта инструкция не означает, что изменения уже опубликованы. Подготовлена ветка от `main` `3fb107421b11dbe332f9621573426060bc84198d`. На SpaceWeb в рамках этой задачи ничего не менялось; настоящие письма не отправлялись.

## Что нужно подтвердить перед публикацией

1. PHP **8.2+**, расширения `mbstring`, `openssl`, `ctype`, `filter`, `hash`; работа PHP именно у murrif.ru. Официальная справка SpaceWeb подтверждает доступность PHP и SMTP у провайдера, но не выбранную версию/настройку этого сайта.
2. Существующий SMTP-ящик, его провайдер, хост, порт и защищённый режим, логин, адрес From и ящик получателя. Не предполагать, что публичный Gmail автоматически является согласованным серверным получателем. Пример для существующего ящика SpaceWeb: `smtp.spaceweb.ru:465`, SMTPS, From совпадает с логином. DNS, MX, SPF, DKIM и DMARC автоматически не менять; проверить их для согласованного отправителя отдельно.
3. Возможность создать закрытую папку рядом с `public_html`, разрешения PHP на неё, `flock` и атомарный `rename`. Для murrif.ru это ещё не проверено. Путь установки сайта указан в прежних отчётах; сверить его в панели перед загрузкой.
4. Фактический почтовый маршрут, условия обработки у почтового провайдера и хостинга, состав/сроки access/error logs и применимость юридических требований к оператору. `privacy.html` и `consent.html` — **проекты**, не юридическое заключение. Старые реквизиты и срок «до 1 года» не придумывались и не перепроверялись; владелец должен подтвердить их актуальность. Убрать отметки о проекте и поставить реальную дату публикации только после согласования.
5. Согласовать один конкретный тест: отправитель, получатель и неперсональное тестовое содержимое. Пароль в чат не передавать. Настроить его в защищённом редакторе файлов хостинга или по SSH в закрытом конфиге.

## Подготовка пакета

На машине с PHP 8.2+ и Composer 2:

```sh
composer --working-dir=server install --no-dev --prefer-dist --no-plugins --no-scripts --optimize-autoloader
composer --working-dir=server audit --no-dev --locked
php scripts/package.php /absolute/new/murrif-release
```

Используется только PHPMailer **7.2.0**, версия и Git reference закреплены в `server/composer.lock`. Это поддерживаемая SMTP-библиотека с MIME/Unicode и проверкой TLS. Собственного SMTP-клиента и вызовов PHP `mail()` нет. Не запускать `composer update` при публикации; обновление зависимости — отдельная проверка.

Пакет имеет две соседние папки:

- `public_html/`: три HTML, `css/`, `js/`, `api/contact.php`, шрифты с лицензиями, фотографии/скриншоты, `robots.txt`, `sitemap.xml`, прежний `.htaccess`.
- `private/murrif-contact/`: код обработчика, `vendor/`, пример конфигурации, lock-файл и CLI-очистка. **Никогда не загружать эту папку внутрь `public_html`.**

Скрипт использует список разрешённых файлов. Не копирует настоящий `config.php`, `.env`, runtime, тесты, документацию, `.git`, служебный локальный просмотр или подставной транспорт. Если Composer на хостинге отсутствует, установить зависимость локально под совместимой версией PHP и загрузить полученный `vendor` в закрытую папку.

## Конфигурация

В закрытой папке скопировать `config.example.php` в `config.php`, заполнить поля и сохранить `enabled=false` до проверок. Создать случайный секрет на сервере командой `php -r 'echo bin2hex(random_bytes(32)), PHP_EOL;'`, вставить в `secret`, не включать вывод в отчёты.

По умолчанию публичный обработчик ищет `../private/murrif-contact` относительно корня сайта. Альтернатива — серверная переменная `MURRIF_CONTACT_DIR` с абсолютным закрытым путём. Запрос посетителя не может выбрать путь или SMTP-конфигурацию. Обработчик отказывает, если код или разрешённый путь хранения оказываются внутри публичной папки.

Права: каталоги с конфигурацией и данными — `0700`, `config.php`, журналы и состояние — `0600` (либо минимальные эквивалентные права для подтверждённого пользователя PHP). Публичные файлы обычно `0644`, каталоги `0755`. Не использовать `0777`. Проверить модель пользователя PHP в SpaceWeb до назначения прав. Приватный `.htaccess` — дополнительная защита, а не замена размещению вне document root.

Добавить ежедневное выполнение `php /absolute/private/murrif-contact/cleanup.php` через панель cron. Удаление технических записей также выполняется при следующем валидном запросе; без cron физическое удаление при отсутствии трафика не гарантируется. Состояние повторов живёт 24 часа, IP-счётчики 15 минут, общий счётчик час; диагностика ограничена 256 КиБ и очищается от событий старше 7 дней ежедневной задачей. Не удалять состояние повторов при обычном обновлении кода.

## Модель защиты и ограничения

- POST JSON либо URL-encoded, до 32 КиБ. Только известные строковые поля; Unicode, допустимые услуги и контакты проверяются на сервере. Имя до 80, контакт до 160, сообщение до 4000 символов. Телефон и Telegram не требуют email. Клиентская проверка email предварительная; окончательная — серверная.
- Origin (или same-origin Referer при отсутствии Origin) сверяется с явным списком. CORS не включён. Это препятствие для чужих браузерных страниц, **не защита от ботов**. Ответ использует `Referrer-Policy: same-origin`, чтобы исправление формы без JS не теряло источник запроса.
- Honeypot скрыт через `hidden`, исключён из клавиатуры/скринридера/автозаполнения. Заполненный honeypot отклоняется без фиктивного успеха.
- Лимит: 5 новых валидных сообщений с одного сетевого адреса за 15 минут; 60 всего за час. `X-Forwarded-For` игнорируется. Если SpaceWeb передаёт общий адрес прокси как `REMOTE_ADDR`, лимит может объединить посетителей: сначала подтвердить модель прокси, не доверять произвольным заголовкам. В состоянии хранится HMAC адреса, не сырой IP.
- `flock` и запись через временный файл/`rename` обеспечивают согласованность конкурентных запросов. Состояние ограничено по количеству; повреждённое или недоступное хранилище блокирует отправку.
- До SMTP фиксируется `pending`. Повтор той же полезной нагрузки в течение 24 часов не отправляет ещё одно письмо, даже с новым ключом или без JS. Один ключ нельзя применить к другому сообщению. Состояние `accepted` возвращает подтверждение, `pending/uncertain` — предупреждение. На сбой после возможного принятия не следует автоматическая повторная отправка. Это не обещание гарантированной однократной доставки: у SMTP нет транзакции с локальным файлом.
- From/To фиксируются конфигурацией. Проверенный email может стать Reply-To, остальные контакты остаются только в текстовом теле. Текст, выбранная услуга, рекомендация квиза и отметка согласия включаются в письмо.
- SMTP: подключение/ожидание 5 секунд, предел ответа команды 8 секунд, проверка сертификатов включена. PHP запрашивает лимит выполнения 25 секунд, браузер ждёт до 35 секунд. Это не гарантированный общий wall-clock SMTP timeout: особенности PHP/хостинга и несколько SMTP-команд влияют на длительность. Обрыв оставляет безопасную запись `pending`; автоматического повтора нет.
- Записи состояния не содержат имени, контакта, текста обращения. Диагностика содержит только время, случайный ID и код результата; содержимое SMTP-ошибок не записывается. Отдельно проверить журналы самого хостинга.
- Без JS ошибки возвращают HTML с экранированными сохранёнными полями. Успех — HTTP 303 на GET с подписанной квитанцией на 10 минут. В URL нет полей обращения. Обновление квитанции не выполняет POST.

## Проверки на хостинге перед включением

1. Сделать резервную копию текущего публичного каталога вне document root. Сохранить конфигурацию и состояние отдельно, не выгружать их в Git.
2. Загрузить закрытую часть, затем публичные ресурсы и обработчик. Сверить размеры/хеши, убедиться в отсутствии PHP-исходников в ответах.
3. Пока отправка выключена, GET к `/api/contact.php` должен вернуть 405 при установленной закрытой части; валидный POST — 503. Ошибочные поля — 422. Не считать это проверкой SMTP.
4. Убедиться, что `/server/config.php`, `/private/murrif-contact/config.php`, `/server/vendor/`, `/private/murrif-contact/var/state.json`, `/.git/config`, архивы и журналы недоступны: 403/404, без содержимого. Решающая проверка — реальный путь закрытого каталога вне `public_html`.
5. Проверить CSS/JS/шрифты 200, все страницы, меню, квиз, no-JS форму, новые версии query-параметров CSS/JS. Canonical/robots/sitemap сохранены. Сервисные ответы намеренно `noindex`; публичные страницы — без `noindex`.
6. После согласования документов и конкретной тестовой отправки включить `enabled`, выполнить один тест. Отдельно зафиксировать: принятие SMTP, наличие во входящих/спаме, Reply-To, повтор того же запроса без второго письма. Без доступа к ящику доставку не утверждать.

## Откат

До слияния достаточно оставить новую ветку и не менять `main`. После слияния — обратный коммит `git revert` только коммитов этой задачи, без `reset --hard` и force push. На хостинге восстановить прежние публичные файлы из резервной копии, затем выключить обработчик. Закрытый конфиг и состояние не удалять автоматически: записи защищают от повторов при повторном включении. Вернуть прежние тексты privacy/consent вместе с прежним механизмом формы.
